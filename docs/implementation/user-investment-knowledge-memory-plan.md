# 用户投资知识注入与智能体记忆方案

日期：2026-05-29

## 目标

让用户可以通过自然语言把自己的市场观察、行业经验、风险偏好和交易纪律注入系统，并在后续监控、分析和交易建议中被智能体检索、引用、验证和更新。

这个功能不是简单把用户输入拼进 prompt，而是建立一套可审计的投资知识记忆层：

- 用户通过对话输入观察。
- 大模型把观察抽取为结构化规则。
- 用户确认后规则才生效。
- 系统在分析相关股票、行业、主题时检索这些规则。
- 输出建议时明确引用规则、证据和置信度。
- 后续用真实行情和事件复盘规则有效性。
- 过期、冲突或验证失败的规则会降权或失效。

## 当前项目可复用基础

项目已有两类基础能力：

- `tradingagents/agents/utils/memory.py`：ChromaDB 向量记忆组件，可用于相似场景检索。
- `app/services/internal_message_service.py`：MongoDB 内部消息存储，可保存结构化研究笔记、研报、观察和策略材料。

建议不要直接只用 ChromaDB 做唯一存储。MongoDB 做权威结构化知识库，ChromaDB 做语义检索索引。

## 数据模型

建议新增 MongoDB 集合：

### `user_investment_observations`

保存原始对话输入和抽取结果。

核心字段：

- `observation_id`
- `user_id`
- `raw_text`
- `extracted_rules`
- `created_at`
- `source`: `user_chat`
- `status`: `draft/pending_user_approval/approved/rejected/archived`

### `investment_knowledge_rules`

保存已确认的投资知识规则。

核心字段：

- `rule_id`
- `user_id`
- `title`
- `scope.market`
- `scope.sectors`
- `scope.symbols`
- `conditions`
- `risk_signal`
- `opportunity_signal`
- `preferred_action`
- `avoid_action`
- `confidence`
- `evidence_links`
- `version`
- `status`: `active/inactive/expired/conflicted`
- `valid_from`
- `valid_until`
- `created_at`
- `updated_at`

### `investment_rule_outcomes`

保存规则复盘结果。

核心字段：

- `rule_id`
- `symbol`
- `triggered_at`
- `decision_context`
- `suggested_action`
- `actual_return_1d`
- `actual_return_5d`
- `actual_return_20d`
- `outcome_label`: `helpful/harmful/inconclusive`
- `review_notes`

## 工作流

### 1. 对话输入

前端新增“投资知识库/策略教练”入口。用户可以像聊天一样输入观察，也可以让系统追问：

- 这个观察适用于哪些市场？
- 适用于哪些行业或股票？
- 什么情况下触发？
- 触发后应买入、卖出、减仓还是观望？
- 有哪些反例？
- 有效期多久？

### 2. 结构化抽取

用当前已配置的大模型把自然语言转成结构化规则。抽取后必须展示给用户确认，不自动生效。

抽取规则：

- 观点和事实分开。
- 条件和动作分开。
- 适用范围必须明确。
- 必须给出置信度和有效期。
- 如果缺少触发条件，系统应追问。

### 3. 人工审批

用户确认后规则进入 `investment_knowledge_rules`，状态变为 `active`。未确认内容只能作为草稿，不能影响交易建议。

### 4. 检索注入

在以下场景检索相关规则：

- 单股分析。
- Watchlist 自动监控。
- 行业/主题扫描。
- 交易前审批。
- 风险审计模型复核。

检索条件：

- 股票代码匹配。
- 行业/主题匹配。
- 市场匹配。
- 当前行情/新闻满足规则条件。
- 向量相似度匹配。

注入方式：

- 把最多 3-5 条最相关规则作为 `user_strategy_context` 提供给智能体。
- 输出报告必须列出引用了哪些用户规则。
- 如果规则和当前数据冲突，报告必须说明冲突。

### 5. 审计校验

审计模型检查：

- 模型是否引用了真实存在的用户规则。
- 是否篡改了用户规则含义。
- 规则是否仍在有效期内。
- 当前数据是否真的满足触发条件。
- 是否把用户经验当成事实。

### 6. 复盘成长

每天或每周复盘被触发的规则：

- 如果规则触发后避免了大跌，提升规则置信度。
- 如果规则导致错过持续上涨，降低规则置信度。
- 如果规则长期无触发或环境变化，标记为待复审。
- 任何自动调权都要记录原因，重要规则变更需要用户确认。

## 分阶段实现

### 第一阶段：知识录入和分析注入

- 新增用户投资知识库页面。
- 新增对话式录入 API。
- 新增规则抽取 API。
- 新增用户确认/拒绝 API。
- 在单股分析和 watchlist 扫描中读取已确认规则。
- 分析报告显示“引用的用户规则”。

### 第二阶段：条件触发和审计

- 规则条件与行情、新闻、公告、行业标签联动。
- 监控扫描时输出规则触发原因。
- 审计模型校验规则引用和数据真实性。
- 支持规则冲突提示。

### 第三阶段：复盘和自我改进

- 建立 `investment_rule_outcomes`。
- 自动计算规则触发后的 1/5/20 日结果。
- 给规则打 `helpful/harmful/inconclusive` 标签。
- 生成每周规则复盘报告。
- 支持用户根据复盘一键修改规则。

## 设计原则

- 用户知识必须可见、可编辑、可删除。
- 用户知识必须先确认后生效。
- 模型不能私自永久记忆未经确认的对话。
- 模型输出必须区分“用户经验”“市场事实”“模型推断”。
- 任何交易建议都要说明是否引用用户规则。
- 规则必须有有效期和复盘机制，避免旧经验污染新市场。

## 非目标

- 第一阶段不做模型微调。
- 第一阶段不让模型自动改写用户策略并立即生效。
- 第一阶段不让用户知识直接触发自动交易。
- 第一阶段不把所有聊天内容无条件长期保存。
